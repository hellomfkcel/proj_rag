

# AI 辅助编程 / 多‑Agent：对话纪要 + 工具清单（含已公开的 token/费用信息）

## TL;DR（把我们这段对话压成 6 句话）
1. “Codex 很强、全能”这类推荐话术本质上不科学：**AI 编程能力强≠能端到端把工程干好**，尤其不等于能替你做架构决策。  
2. 你提出的判断很工程化：**AI 辅助编程最终只能看产品（可运行、可测试、可维护），过程指标在 agent 时代基本失真**。  
3. **多‑Agent 讨论**的核心价值在“没思路时的发散/对抗式推演”；一旦你已经有思路，它往往变成“高成本噪音”。  
4. 费用暴涨通常不是“模型突然变贵”，而是你把“想清楚/定方案”的工作外包给 agent 群体：**每一步都在反复搬运上下文 + 产生大量工具输出**。  
5. 你提到的“很烧 token + 大量缓存命中”是典型 agent 负载形态：**输入侧靠 prompt caching 扛住成本，输出/推理/工具轨迹仍然可能很贵**（而且 cache 一失效会出现一次性“昂贵回合”）。  
6. 结论就是你说的：**慎用多‑Agent；没思路时试一下，正常开发没必要默认开。**

## 1) 为什么“多‑Agent 才会烧成那样”：结构性放大机制（你已经抓到关键）

你用 `anthropics/claude-quickstarts` 里的 `autonomous-coding` 跑过一次之后理解到的点非常关键：**当你不自己做架构/拆解，只给想法，让多个 agent 去讨论、互相质疑、再落地**，token 会被“讨论回合数 × 上下文搬运 × 工具输出”放大。

在 Anthropic 的 `Autonomous Coding Agent Demo` 里，它明确就是一个“两 agent（initializer + coding agent）+ 多 session 续跑”的 harness：  
- Session 1（initializer）会读 spec，然后生成 `feature_list.json`（默认 200 条测试用例/特性列表），并初始化项目结构与 git。  
- Session 2+（coding agent）会“按 feature_list 一条条实现”，每轮迭代 **5–15 分钟**；把 200 条做完通常要“很多小时”。  
  这类长跑，本质上就是在把“产品经理 + 架构师 + 开发 + 测试”一部分工作交给 agent 循环来做；只要循环次数上去，token 就很难小。

> 你原话的结论可以写成一句工程原则：  
> **AI 是放大器：放大“你已有的方案”最省；替代“你还没想清楚的方案”最贵。**

## 2) “大量缓存命中”到底是什么意思？为什么它既救命、又会坑人

### 2.1 Claude Code：每回合都要重发上下文，cache 用来避免重复“预填充”
Claude Code 官方文档把机制讲得很直白：**模型本身不会跨请求记忆**，所以 Claude Code 每次都会把系统提示、项目上下文、历史消息、工具结果等“全量重发”；prompt caching 通过“前缀精确匹配”复用已经处理过的那部分前缀，减少重复计算与成本。

Claude Code 还给了非常实用的“cache 失效原因清单”，比如：切模型、MCP 服务器连接变化、compact（摘要压缩）、升级 Claude Code 等，都会导致下一回合出现一次“更慢/更贵的 uncached turn”。

并且它提供了可以观察的计数（对“你感觉缓存命中很多”这点很对口）：  
- `cache_creation_input_tokens`：本轮写入缓存的 token（按 cache write 计费）  
- `cache_read_input_tokens`：本轮从缓存读取的 token（大约按标准输入价的 10% 计费）  

### 2.2 OpenAI API：同样是前缀缓存，且有明确 TTL 规则与 `cached_tokens`
OpenAI 的 Prompt Caching 文档同样强调“前缀命中”、以及 `cached_tokens` 字段可观测；并给出典型缓存生命周期：**通常 5–10 分钟不活跃会清，且 1 小时内必清**（不同产品层可能会封装成“自动/延长 TTL”策略）。

## 3) 对你“过程指标意义不大”的补强：研究结论也支持“高成本≠高正确率”

你直觉里其实还有一层更硬的含义：**agentic 运行很贵，但贵不保证更好**。

一篇 2026 年的论文专门研究“agentic coding 任务如何烧 token”，结论包括：  
- agentic 任务在 token 消耗上可比普通 code reasoning / code chat **高出 1000×**量级；  
- token 用量高度随机，同一任务不同 run 可能相差 **30×**；  
- 更高 token 并不必然带来更高准确率，效果往往在中间成本就饱和。  

所以你说“只能看最终产品”，不仅是管理学直觉，也是对“成本‑收益曲线”现实的适配。

## 4) 多‑Agent 工具/框架清单（偏编程/工程），以及**已公开**的 token/费用信息

下面我把“多‑Agent”按三类列：  
- A 类：**一线 coding agent 产品**（官方有定价/成本区间）  
- B 类：**开源 coding agent**（论文/基准里能看到 token 量级）  
- C 类：**多‑Agent 编排框架**（通常不给你“会烧多少 token”的固定数，因为完全取决于你怎么跑）

### A 类：产品级 coding agents（官方披露较多）

| 工具                            | 多‑Agent/并行形态                             | 公开的消耗信息（你能直接引用的）                         | 备注                                       |
| ----------------------------- | ---------------------------------------- | ---------------------------------------- | ---------------------------------------- |
| **Anthropic Claude Code**     | 支持“subagent”（子代理）概念；并且 prompt caching 自动管理 | 企业部署平均约 **$13/开发者/活跃日**、**$150–250/开发者/月**，且 90% 用户低于 $30/活跃日 | 成本受“是否频繁 cache 失效”“上下文规模”“工具输出量”影响很大     |
| **OpenAI Codex（CLI/Web）**     | 可以跑多实例/自动化；并区分 input / cached input / output 三类 token 计费 | OpenAI 给出按 token 计价的 **credits/百万 tokens**表；并称“典型任务”约 **5–45 credits/任务**；平均约 **$100–200/开发者/月**（方差很大，取决于模型、实例数、自动化、fast mode） | 2026‑04‑02 起从“按消息估算”迁移到“按 token 映射 credits”；并在 2026‑04‑23 覆盖到所有 Enterprise 计划 |
| **Cursor（IDE，含并行/后台 agents）** | 文档层明确把 agent 用量视为“按模型 API 成本计费”的使用池      | Cursor 官方给的用量经验：日常 agent 用户通常 **$60–$100/月**总用量；power users 往往 **$200+/月**；并说明 Pro/Pro+/Ultra 分别包含约 $20/$70/$400 的 agent API 用量 | Cursor 把“不同模型 API 成本不同 → 消耗速度不同”说得很明确    |

### B 类：开源 coding agents（能看到“token 量级”）

这里最有用的其实不是“某工具平均多少钱”（很少有官方口径），而是：**在公开基准里，agent 框架跑一次任务大约会到什么 token 量级**。

一个 2026 Findings of ACL 的 repo‑level 任务（SWE‑QA）做了 cost analysis，直接给了“每个问题的输入/输出 token”量级：  
- **SWE-agent**：平均约 **126,026 输入 / 4,627 输出 tokens / 问题**  
- **OpenHands**：平均约 **87,045 输入 / 1,930 输出 tokens / 问题**  
  并且论文明确指出：agent-based 方法相对 direct prompting 大约会出现**数量级**的 token 增长。

这类数字虽然不是“你生成一个 Web 项目要多少”，但对判断“为什么 agent 一跑就爆”非常有参考价值：**因为光一个“理解仓库 + 多步工具调用”的问题就能到 10^5 级输入 tokens。**

### C 类：多‑Agent 编排框架（一般不提供固定 token 消耗数）

| 框架                       | 定位                                       | 与 token 消耗的关系（现实结论）                      |
| ------------------------ | ---------------------------------------- | ---------------------------------------- |
| **AutoGen（Microsoft）**   | 多‑agent 应用框架；官方 repo 说明其用于 multi-agent patterns（two-agent chat、group chat 等），但已进入 maintenance mode，建议新用户用 Microsoft Agent Framework | 框架本身不决定成本；**你的 agent 数、回合数、是否共享上下文、工具输出量**决定 token。 |
| **LangGraph（LangChain）** | 以“图/状态机”方式编排单/多 agent 工作流，支持 multi-agent/hierarchical control flows | 优点是更容易加“门禁/人工审批/中止条件”，从而把“无意义循环”扼住，间接省 token。 |
| **CrewAI**               | 角色化协作的多 agent 框架（crew/flow）              | 常见坑是“每个角色都要读一遍大上下文”，如果没有严格的上下文分发策略，很容易指数级膨胀。 |

## 5) 把你的经验落成“可执行的使用规范”（减少多‑Agent 不必要燃烧）

### 5.1 什么时候值得开多‑Agent
适合（值得烧）：  
- **完全没思路**：需要快速发散出 2–3 套可行架构候选；  
- **高风险决策**：需要红队/反对者角色专门找漏洞、找边界条件；  
- **你很明确要“探索空间”**，并且能接受“讨论成本”。

不适合（性价比差）：  
- 你已经有清晰架构/模块边界，只需要“把砖搬完”；  
- 需求本身还不稳定，讨论越多越容易把噪音固化成技术债。

### 5.2 一个最省 token、但仍然工程化的工作流（推荐默认）
1. **你先写 1 页架构草图**（模块/数据流/边界/约束/不做什么）。  
2. 单 agent：让它把草图变成 `README + 文件树 + TODO 列表 + 测试策略`。  
3. 单 agent：按 TODO 一条条实现（每条都跑测试），你只 review 关键 PR。  
4. 当出现“卡住/分歧/风险点”时，再临时拉一个 critic agent 做一次对抗审查，然后收敛回单 agent 执行。

### 5.3 对 `autonomous-coding` 这类 harness 的“省钱开关”
Anthropic 的 demo 本身就给了两个非常直接的降成本手段：  
- 用 `--max-iterations` 做硬上限（防止无限跑）。  
- 把 initializer 默认要求的 **200 features**改成 20–50（它也明确写了“为了演示更快可以改”）。

## 6) 附：如何把“token 消耗”从感觉变成可审计数据（非常建议你做）

你已经在用 Claude Code / agent harness 了，下一步最有价值的是把“每次跑 agent 的成本”变成你能复盘的指标：  
- 记录每次任务：输入/输出 token、cache read/create token、耗时、最终是否交付（测试通过/可部署/可维护）。  
- 你会很快发现：**最烧的不是写代码，而是“探索仓库 + 多步工具输出 + 多角色互相转述同一份上下文”**。

如果你想跨工具统一看 token（Claude Code、Codex CLI、Cursor 等），也存在一些“本地读取日志、只记录 token 计数、不收集内容”的统计工具（适合做成本回归分析）。
