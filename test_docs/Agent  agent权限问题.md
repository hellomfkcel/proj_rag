# Agent 权限问题

## 一、核心论点：Agent 权限的本质

Agent 的权限问题，本质上不是一个独立的新问题，而是**资源访问的授权问题在新入口上的投影**。

判断逻辑应当是：

- **如果公司已有完整的数据管理流程**：只需把 agent 在访问数据时纳入到这个既有的管理流程中来，复用已有的治理体系即可。
- **如果公司没有完整的数据管理流程**：则要上升到公司数据管理建设的问题，这不再是单纯的 agent 权限问题。

换言之，考察 agent 权限，考察的不是 agent 本身，而是**对数据治理体系的理解深度**。直接跳到"最小权限原则""沙箱隔离""工具调用审计"这些 agent 专属的表层概念，是术而非道。

## 二、成熟数据治理体系下的接入方案

以 **Polaris + Trino + S3** 这套成熟数据湖架构为例：

Polaris 作为 Iceberg Catalog，本身就承担了 metadata 层的权限管理——哪个 principal 能访问哪个 namespace、table、view，都在 catalog 层定义好了。Trino 通过 Iceberg connector 查询时，Polaris 的权限检查自然嵌入进来。

因此 agent 的接入方式就是：

> **agent 持有（或代持）用户凭证 → 带着这个身份去查 Trino → Polaris 按既有规则鉴权**

不需要为 agent 单独设计权限体系。

### 代持身份的两种粒度

| 模式 | 说明 | 审计特征 |
|------|------|----------|
| **Impersonation（身份扮演）** | agent 用用户真实身份访问 | 日志里看到的是用户操作，权限边界完全等同于该用户 |
| **Service Account（服务账号）** | agent 有自己的 principal，但被授予等同于某用户/角色的权限 | 审计上能区分"人操作"与"agent 操作"，排查更清楚 |

如果对审计有要求，Service Account 模式更干净。Polaris 在 principal roles 和 catalog roles 的映射上支持这种细粒度设计，架构上是顺的，关键是把 agent 的 principal 注册和角色绑定流程规范化。

## 三、重新认识"数据湖"

数据湖以前是大数据范畴的概念，是**规模驱动**的——数据量大了、OLTP 存不下查不动，才需要一个地方把数据"倒"进去。

但现在，数据湖更应被理解为一套**数据管理的方法论与架构范式**，是**数据治理的基础设施蓝图**。它回答的核心问题包括：

- 数据存在哪、怎么组织
- 谁能访问什么、怎么鉴权
- 数据从哪来、怎么流转、血缘怎么追踪
- 如何保证数据质量与一致性

这些问题从有数据的第一天就存在，**与数据量无关**。

**关键认知纠偏**：不是"有了很多数据才上数据湖"，而是"建设之初就应按数据湖的思路设计"。规模可以小，但架构要对。很多公司数据治理一塌糊涂，恰恰因为早期觉得"数据量还不够大，不需要上数据湖"，等数据真多了再补，成本极高、历史包袱极重。

## 四、从数据治理到流程治理

严格来说，数据治理问题不仅是数据管理问题，本质是**流程治理**。

未来大量的数据访问、工具调用将由 agent 发起。哪些 agent、哪些用户，能调用哪些工具、访问哪些地址、执行什么样的操作——这些都应当被管控。

数据访问可以统一收敛到 Polaris，因为数据天然有**统一的访问入口和资源模型**（catalog → namespace → table）。但**工具调用没有这种天然的收口**，它是分散的、异构的，这才是真正的难点。

### 工具调用治理的三层解法

**第一层：把工具调用也建模成"资源 + 动作"**

工具调用看似异构，抽象后都是 `谁(principal) 对 什么(resource) 做 什么操作(action) 在什么条件下(context)`。这正是 ABAC / PBAC 的标准范式，可以用统一的策略引擎来管，例如 OPA（Open Policy Agent）、Cedar（AWS 的策略语言）。

**第二层：策略决策点要插在调用链路的关键卡口上**

光有策略引擎不够，得有地方拦截。在 agent 场景下，卡口通常是：

- **MCP Gateway / 工具网关**：所有工具调用经过统一代理，在此做鉴权和审计——相当于在工具层做了一个类似 Polaris 的"统一入口"。
- **Agent Runtime 内置的 guardrail**：在 agent 框架层拦截工具调用请求。

**第三层：身份要能穿透**

最关键也最难。agent 调用工具时必须携带可信的身份链路：是哪个用户授权了哪个 agent，agent 又代表谁去调这个工具。需要 token 传递 / 身份委托（delegation）机制，例如 OAuth 的 token exchange，或 SPIFFE / SPIRE 这类工作负载身份方案。

### 工具调用治理比数据访问多出的两个难题

1. **副作用不可逆**：查数据是只读的；调工具可能是写操作、发邮件、转账。鉴权失败的代价完全不同，需要更细粒度的控制，甚至引入人工审批环节（human-in-the-loop）。
2. **组合风险**：单个工具调用都合规，但组合起来可能造成危害（如先查敏感数据再外发）。这是数据访问鉴权模型覆盖不到的，需要在 agent 行为层面做意图与序列的管控。

### 阶段性结论

> **数据访问治理是已经解决的问题，工具调用治理是正在定义的问题。**

工具调用的"Polaris"目前尚无事实标准，但形态正在收敛，大概率会是：**MCP Gateway + 统一策略引擎（OPA / Cedar）+ 工作负载身份体系** 的组合。MCP 协议的流行加速了这件事，因为它第一次让"工具调用"有了相对统一的协议层，有了协议层就有了插策略和审计的天然位置。

## 五、Polaris 能否管控向量数据库与图数据库？

**结论：目前不能直接管控，但边界正在被两种力量撬动。**

### 为什么默认管不了

Polaris 的本质是 Apache Iceberg 的 REST Catalog 实现，管理的是 catalog → namespace → table → view 这套 Iceberg 资源模型，鉴权是 RBAC 作用在这些实体上。

向量数据库（Milvus、Qdrant、Weaviate）和图数据库（Neo4j、NebulaGraph）有**完全不同的资源模型和访问协议**——不说 Iceberg REST，不是 table/namespace 抽象。Polaris 没有 connector 或协议层去触达它们。且 Iceberg 本身目前对向量、图像等重数据模式支持还不好，社区仍在探索改造，尚未破局。

### 两条正在打通的路径

**路径一：图数据库——通过 zero-ETL 引擎反向接入 Polaris 治理**

以 PuppyGraph 为代表：它不是让 Polaris 去管图数据库，而是**干脆不要独立的图数据库**。它提供 zero-ETL 图查询引擎，直接连数据源，让用户能在 Polaris 实例上直接跑图查询，同时保持细粒度治理与血缘。

图能力被做成 Polaris 之上的**查询层**，数据仍躺在 Iceberg / S3 里，鉴权仍走 Polaris，图查询天然继承 Polaris 治理。性能可观——支持五亿条边上 10 跳邻居查询，2.26 秒返回。

代价：必须接受"图能力是计算层、存储还是湖"这个范式，而非使用真正独立的原生图数据库。

**路径二：向量 / 图作为独立系统——Polaris 管不了，需别的收口**

若坚持用独立的原生向量库或图库（很多场景确实需要，如向量库的 HNSW 索引、图库的原生图存储引擎，这些湖架构给不了），则 Polaris 这条线断了，要回到工具调用治理层面解决：

- 在各自系统内做权限（Milvus、Neo4j 都有自己的 RBAC）——治理**碎片化**。
- 或在更上层架统一策略引擎（OPA / Cedar）+ 网关，把对向量库、图库的访问也纳入统一鉴权——但这已不是 Polaris 的活，而是一个跨系统的授权平面。

### 区分标准与总体结论

本质区别在于：**数据能否被纳入 Iceberg 的资源模型并通过 REST Catalog 暴露**。能，Polaris 就管得了；不能，就得靠工具调用层那套更通用、但尚未标准化的治理体系。

| 数据类型 | 能否被 Polaris 收口 |
|----------|---------------------|
| 结构化数据（Iceberg table） | ✅ 能统一收口，治理已解决 |
| 图数据 | ⚠️ 走 zero-ETL 范式可拉入治理伞下；用独立图库则掉出去 |
| 向量数据 | ❌ Iceberg 尚未适配好，独立向量库基本只能靠自身 RBAC 或上层统一授权平面 |

> **Polaris 不是数据治理的终点，而是"结构化湖数据"这一块的治理终点。**
>
> 完整的 agent 数据治理，注定是 **Polaris（管湖数据）+ 统一授权平面（管其余异构系统与工具调用）** 的组合，无法靠单一一个东西收口。
